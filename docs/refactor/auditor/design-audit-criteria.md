# Design Audit Criteria

> **🔒 FROZEN (2026-06-01):** 본 기준은 동결되었다. C-1~7 / F-1~11 / A-1~5 / P-1~13이 최종이다. **새 criterion을 추가하지 않는다.** 동결 이후 감리는 (a) 명백한 설계 결함만 보고하고, (b) 코드펜스·문장↔bullet 같은 형식 nit는 PASS로 처리한다. 설계는 "Sonnet이 이 문서로 구현을 시작할 수 있는가"를 기준으로 충분하면 통과다. 추가 보강보다 **실행(구현)과 execution-audit**으로 진행한다.

> Auditor는 Designer가 작성한 **설계 문서**가 충분히 정밀하고 병렬 실행 가능한지를 확인한다.
> 본 기준만으로 판정 가능해야 하며, 외부 추론은 금지한다.

## 0. 진입

Auditor는 다음 한 줄로 호출된다:

```
audit-design --target {feature|adr|phase}/{filename}.md
```

응답은 아래 양식.

```
TARGET: ...
VERDICT: PASS | FAIL
FAIL_REASONS:
  - <criterion-id>: <인용 또는 부재 근거>
  - ...
PASS_NOTES:
  - <selectivley, 특이사항>
```

## 1. 공통 (모든 문서 종류)

- [ ] **C-1**: 문서 상단 frontmatter가 정확한 키 (`status`, `designer`, `auditor_status`, `last_updated`, ID 필드) 보유
- [ ] **C-2**: 템플릿의 모든 섹션 헤더가 존재 (삭제 금지)
- [ ] **C-3**: 모든 코드 블록에 언어 태그 (` ```python`, ` ```bash` 등)
- [ ] **C-4**: 인용된 파일 경로는 절대 또는 프로젝트 루트 기준 상대 경로
- [ ] **C-5**: 라인 번호 인용시 `path:NN` 형식
- [ ] **C-6**: 결정·주장은 명령형/단정형 (예: "한다", "필수"). 추측·미정 표현 0건 또는 별도 "미해결" 섹션에 격리
- [ ] **C-7**: 한국어/영어 혼용 일관성 — 동일 개념은 동일 표기

## 2. Feature Doc 전용

- [ ] **F-1**: "As-is / To-be" 한 줄 요약 모두 채워짐
- [ ] **F-2**: 현재 구현 분석에 **Streamlit API 전수 표**가 있고 각 row가 위치(file:line)와 용도 기재. 단, 백그라운드 데몬·CLI 등 UI를 갖지 않는 feature는 "본 feature는 UI 미보유 (백그라운드/CLI)"를 명시적 한 줄로 적고 표 자체는 생략 또는 단일 "해당 없음" row 허용
- [ ] **F-3**: 외부 API 호출은 URL·메서드·파라미터·응답 형식·실패 응답까지 명시
- [ ] **F-4**: 새 구현 매핑에 **URL & HTTP 메서드**, **Flask 핸들러 시그니처**, **템플릿 경로**가 모두 존재. 단, 백그라운드 데몬·CLI feature는 다음 두 조건을 모두 충족하면 본 항목을 충족한 것으로 본다: (a) 4.1 섹션에 CLI 서브커맨드 시그니처(이름·파라미터·예시) ≥1건 명시 (b) 다른 feature를 통해 HTTP 노출되는 경우 그 feature ID를 인용 (예: F09 데몬 상태는 F04에서 노출)
- [ ] **F-5**: 도메인 서비스 함수 시그니처가 타입 힌트 포함
- [ ] **F-6**: 실시간 화면이면 폴링간격 또는 SSE 토픽, 부분갱신 selector가 명시
- [ ] **F-7**: AC 체크리스트가 ≥3건이며 각 항목 옆에 **검증 방법**이 적혀있음 (자동 명령 우선)
- [ ] **F-8**: 단위 테스트 케이스 ≥3건 제시. 각 케이스는 **(a) 케이스 이름 + (b) 무엇을 어떤 조건에서 검증하는지 자연어 1줄 설명**을 모두 가진다. 함수명만 나열하면 FAIL (감리가 케이스 의도를 자연어로 설명할 수 있어야 함)
- [ ] **F-9**: 영향 받는 다른 feature doc ID가 나열됨 (없으면 "없음" 명시)
- [ ] **F-10**: "관찰된 결함·악취"가 있다면 가설별로 분리되어 있음 (혼합 1줄 금지)
- [ ] **F-11**: 사람 touch point(화면/폼/버튼/CLI)가 있으면 §1에 TP-ID로 나열·링크하고 대응 `touchpoints/TP-*.md`가 존재한다 (UI 없는 백그라운드 feature는 "사람 touch point 없음" 명시)

## 3. ADR 전용

- [ ] **A-1**: "결정" 섹션이 단정문 1-2줄로 종결
- [ ] **A-2**: 대안 ≥2건, 각 대안에 장점·단점·기각사유 모두 존재
- [ ] **A-3**: "결과" 섹션에 긍정 영향과 부정 영향이 모두 채워짐 (부정 영향 "없음" 시 그 근거 명시)
- [ ] **A-4**: 검증 방법이 실행 가능한 명령으로 적혀있음
- [ ] **A-5**: supersedes/superseded_by 메타가 set (없으면 null 명시)

## 4. Phase Doc 전용 (가장 엄격)

- [ ] **P-1**: Work Item이 **2건 이상** (1건이면 Phase로 격리할 이유 의심)
- [ ] **P-2**: 각 work item이 **단일 산출물 경로**를 가진다 (복수 파일은 단일 모듈일 때만 허용, 명시)
- [ ] **P-3**: 모든 work item에 명령형 지시사항이 ≥3 step 분해되어 있음
- [ ] **P-4**: 모든 work item에 AC ≥2건과 검증 명령이 존재
- [ ] **P-5**: 의존성 그래프에 사이클이 없음 (Auditor가 손으로 트레이스)
- [ ] **P-6**: "병렬화 그래프" 섹션에 **최소 1개 동시 가능 그룹**이 식별됨 (전 work item이 일렬이면 분해 부족 의심)
- [ ] **P-7**: 모든 L (>2시간) work item에 분해 시도 또는 분해 불가 사유 명시
- [ ] **P-8**: Phase의 종료 조건이 모든 work item의 AC 합집합을 cover (누락 0건)
- [ ] **P-9**: 시작 조건이 의존 Phase·ADR·Feature를 명시적으로 인용
- [ ] **P-10**: 리스크와 롤백 절차가 빈 칸이 아님
- [ ] **P-11**: 테스트를 산출물로 갖는 work item은 각 test case마다 **(a) 케이스 이름 + (b) 검증 의도 자연어 1줄**을 기재한다. 감리(Auditor)가 그 설명만 읽고 "이 테스트가 무엇을, 어떤 입력/조건에서, 무엇이 참이어야 통과하는지"를 세부적으로 설명할 수 있어야 한다. 이름만 나열되어 의도가 불명한 케이스가 1건이라도 있으면 FAIL
- [ ] **P-12**: 각 종료 조건(EC)이 work item AC를 1:1로 인용하는 **EC ↔ AC 매핑 표**가 존재하고, 모든 work item AC가 ≥1개 EC에 매핑됨 (누락 0건)
- [ ] **P-13**: 사람 touch point를 산출/변경하는 work item(특히 P4 web)은 대응 `touchpoints/TP-*.md`를 산출물에 포함한다

## 5. 판정 규칙

- 모든 적용 항목 PASS → 전체 PASS
- 1건이라도 FAIL → 전체 FAIL (부분 통과 없음)
- FAIL 시 Designer는 지적된 criterion-id 단위로 수정 후 재제출
- Auditor는 같은 문서 재감리 시 이전 PASS 항목도 재확인 (regression 방지)

## 6. Auditor 자신의 제약

- 코드를 읽지 않는다 (Phase doc의 검증 명령 *내용*만 확인, 실행하지 않음)
- 추측하지 않는다 — 문서에 없으면 FAIL
- 스타일 트집 금지 — criterion-id에 없는 사유로 FAIL 불가
